# Workbench coverage

CodeBridge runs the real VS Code extension host and stands in for the workbench: extensions call
`MainThread*` services expecting an editor on the other end, and the plugin answers. Anything it does
not answer is a hole an extension can fall into, regardless of how good language support is.

This page lists which services are answered and which are not. Counts come from the pinned runtime (VSCodium
1.135.06055) rather than the checked-in id table, because `VsCodeInstallation.rpcIdTable`
extracts ids from the actual bundle and only falls back to the bundled table.

**87 services. 37 implemented, partial or stubbed. 50 not answered.** The unanswered count includes
`MainThreadExtensionService`, whose activation timings are logged but which is otherwise unanswered.

| `MainThreadTreeViews`                                                     | `HostedTreeViews`. The views enabled extensions contribute are read from their manifests, so they are drawn before any host runs: one IntelliJ tool window per view container, a tab per view. Placed by what the container is: the tree views of VS Code's Explorer are nodes of the Project view instead, beside External Libraries (`ExplorerViews`), its Source Control views below the Project view (left, split), its Testing views beside the Run window (bottom, split), an extension's own side-bar container on the right and a panel container at the bottom. A view whose `when` clause does not hold is not shown; clauses read the extensions' `setContext` keys, `config.*` from the running host's settings, and `isWindows`/`isMac`/`isLinux`. Showing a view wakes its extension (`onView:`), starting the host if it has to; items are fetched a level at a time through `$getChildren` and drawn with their codicon or image icon, or a resource's file icon. Selecting an item runs its command (asking `resolveTreeItem` first when it has none); `$refresh`, `$reveal`, `$setTitle` and `$setMessage` are followed, and visibility, expansion and selection reported back. `view/title` and `view/item/context` menus become toolbar buttons and a right-click menu, offered by their `when` clauses (`view`, `viewItem`, context keys) and greyed by `enablement`; only an entry on offer can be run. An empty view shows its `viewsWelcome` content, links clickable. `<view>.focus`, `workbench.view.extension.<container>` and `workbench.actions.treeView.<view>.collapseAll` work. Views in VS Code's Run and Debug container are tabs of the debug sessions of their extension's debugger instead -- CodeLLDB's Modules and Excluded Callers -- made on the backend through the run configuration's additional tabs, which the platform carries to a split-mode client. An item's `inline` entries with an icon are buttons at the right of its row while it is hovered or selected, acting on the selection when the item is in it; entries without an icon stay in the right-click menu. Submenus (`contributes.submenus`) are popup groups in either menu, and in the call stack's, offered by their own entries' clauses and left out with none. Checkboxes are drawn before the icon and ticked by clicking them or with Space, sent as `$changeCheckboxState`; unless the view manages them itself, the fetched items under one follow it and each item above is ticked when all under it are. A view's badge is counted in its tab title. An item whose `resourceUri` is a file stands for that file to the IDE's actions (Copy Path, Open In, Select In), and Select In > Extension View finds the file open in the editor through the items whose files are it or folders holding it, fetching only that path -- the way to library sources such as rust-analyzer's dependencies, which lie outside the project and so have no Project view node. It is offered once the view has fetched an item that is the file or a folder holding it, and selects the deepest folder holding the file when the file itself is not listed. An Explorer view in the Project view is fetched a level at a time as its nodes open, showing "Loading..." until the level is here; items keep the extension's order, an item's command runs on double-click or F4 (one without opens its file), its `view/item/context` entries and the view's `view/title` ones are the Project view's context menu, and its welcome content and message are lines under the view's node. `$reveal` is followed by fetching each level down to the item, and Select Opened File (and Always Select Opened File) then reaches the item through the path the extension revealed for the file's resource, `jdt:` library classes included -- Java Projects reveals the active editor's class on every editor change. Dependencies are not indexed: as in VS Code, rust-analyzer's crate sources are reached through its own view and workspace symbols. Tooltips and messages a `MarkdownString` gives are rendered as hovers are, command links reduced to their labels. Drag and drop and codicons in Markdown are not drawn. ## Two things that constrain all of it

**Results arrive in VS Code's editor shapes**, not LSP's: 1-based `startLineNumber` and
`startColumn`, `MarkdownString` with `&nbsp;`-escaped plaintext, revived URIs. Each feature needs its
own translation, and the wire shapes are internal and undocumented -- read off the bundle, like the
rpcIds. Semantic tokens are the exception that proves it: the workbench passes that payload through
untouched, so it arrives in LSP's own 0-based, delta-encoded form, packed into a `VSBuffer`.

**Editors and tabs are workbench state, not a feature.** The host is told which documents are open,
which editors show them (`addedEditors`, `newActiveEditor`) and what the tab model looks like
(`ExtHostEditorTabs.$acceptEditorTabModel`). None of that draws anything by itself, and all of it is
load-bearing: extensions ask what is *visible*, not what is open. A language client's pull-diagnostics
feature builds its set of resources from `window.tabGroups` and checks it before requesting
`textDocument/diagnostic`, so with no tab model it answers every `workspace/diagnostic/refresh` the
server sends and pulls nothing. A server whose live analysis is pull-based -- rust-analyzer's is --
then appears to produce no diagnostics at all while typing, and only the results it pushes of its own
accord (`cargo check`, on save) ever arrive. Reporting editors is not sufficient on its own; that
feature reads tabs.

**Diagnostics are filed by collection, not just by resource.** `$changeMany` names an owner, and one
extension routinely keeps several -- a client that both receives pushed diagnostics and pulls them
has two, reporting about the same file independently. A push replaces what that owner said before,
never what another owner said, so merging them is what stops a clean `cargo check` erasing live
analysis the moment it lands.

**IntelliJ's own problems go the other way.** An extension that presents diagnostics rather than
producing them -- Error Lens -- reads `languages.getDiagnostics`, and in a Java file no extension
reports anything. `CodeBridgeIdeProblems` sends what the daemon found, weak warnings and up, for each file
the host has in an editor, after every finished pass, over `ExtHostDiagnostics.$acceptMarkersChange`:
the host files it in a mirror collection with no way back, so nothing returns on `$changeMany`.
Problems `CodeBridgeDiagnosticsAnnotator` drew are left out, since the extension that pushed them has them
already. A file's problems are withdrawn when its editor closes.

**Ids are extracted from the running bundle**, so a runtime upgrade does not silently misroute calls.
It can still remove or rename a service, which would surface as a missing entry rather than a wrong
one.
